箱子推不动的时候，我漏看了这一格

大家好，我是「山岚的运维笔记」。

上一篇小人学会了撞墙就停，规矩是懂了。可推箱子这游戏，光会停还不够——它得会推。

今天给它加两个箱子，再教它一句要紧的话：有的格子，看着能进，其实推不动。

**箱子在代码里，就是一组格子号**

先说清楚箱子是什么。它不是屏幕上那个木头方块，那只是影子。箱子在代码里就是一组坐标，两个箱子就两个格子号，跟场景里那两个精灵一一对应。

（图1：场景树里 BoxA / BoxB / Player 三个精灵）

数据归数据，影子归影子。改数据，影子跟着挪；你在编辑器里手动拖影子，数据压根不认账。这个坑我在第 07 篇踩过一次——改了格子号不动位置属性，小人在原地纹丝不动。到箱子这里是同一个道理，只是换了个名字。

**推之前，要看两格**

第 08 篇讲的是「走之前先问一句」。到了推箱子，这一句得问两遍。

一问：人要去的格子，是不是墙？二问：要是那格上蹲着箱子，那箱子要去的格子，进得去吗？

（图2：脚本编辑器里的 find_box 与推箱子判定）

两关都过了才真的动。任何一关不过，直接作废，什么都没发生过。

为什么非得先算再动？你要是先推了箱子再发现推不动，就得把箱子退回去；再往后，箱子上还挂着「推了几步」的统计、还有一步步的撤销记录，回滚起来能让你怀疑人生。先算，判不过就作废，干净。

**找箱子：返回下标，别返回 true 或 false**

这一段我觉得是本篇最值钱的地方。

问「这格有没有箱子」，最直觉的回答是 true 或 false。可你问完这句，下一步十有八九是要挪它。

返回 true，你得再找一遍箱子在数组第几位；返回下标，直接改那一位就搞掂。没找到就返回 -1，这是约定俗成的「没有」。判定的时候老老实实写「不等于 -1」，别图省事拿它当布尔值用，读你代码的人会谢你。

**能不能进，一句话说清**

能不能进 = 不是墙，而且没蹲着箱子。两个条件挤一行，调用的地方一行都不用多想。这个函数现在看着不起眼，后面它是主力：加目标点、加撤销，都得先问它一句。

**跑起来，推一下试试**

起点：人站在左上角，两个箱子排在右边。

（图3：起点，人 cell(1,1)，箱子 A(2,1)、箱子 B(4,1)）

按一下往右。人要去的格上蹲着箱子 A，那就多看一格——A 要去的那格是空地板，进得去。于是 A 被推走一格，人站上原来 A 的位置。

（图4：按第 1 次，推得动，箱子跟着走一格）

再按一下。这回人前面还是箱子 A，可 A 要去的那格，蹲着箱子 B。

箱子推箱子？想多了。这一步整个作废，人和箱子都留在原地。

（图5：按第 2 次，箱子后面还有箱子，纹丝不动）

左右两张我比对过，像素级一模一样。按了，没动，这就对了。

「看两格」画出来是这样：

（图6：黄框人、绿框目标、红框箱子落点）

黄框是人站的格，绿框是人要去的格，红框是箱子要去的那格。红框进不去，整个动作取消。

**最后**

今天其实就一句话：推箱子之前，要看的不是一格，是两格。人要去哪儿，箱子要去哪儿，两处都通得过才动。

现在箱子推得动也推得不动了，可它们还不知道自己该去哪儿。下一篇给箱子找几个「家」——目标点，全部归位就算赢。
